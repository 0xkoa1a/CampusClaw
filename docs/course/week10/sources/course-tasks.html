第 10 课任务清单 · 测试、交付与运行验证

小组任务 · 把散在各课的判据收成一条流水线：一键测试挡住坏提交、容器一键启动、推送即构建、面板看得见三个技能、压测有前后对比、真实用户用过。证据统一归档到仓库根目录 reports/，与根目录 report.md 一起构成最终验收的可查材料——报告正文只写结论与指向

一、开工前：资产盘点

  • 列出本组当前所有可重复执行的命令（make check、make check-security、异步三条判据的执行方式），注明每条上一次执行是什么时候。
  • 对照规约场景做可追溯矩阵：每个场景至少一条用例。空着的场景就是没人守的门，优先补。
  • 确认四个必做技能各有一条行为检查的落点：解题引导不给最终答案 / 教师改分优先 / 错题讲解不贴标准答案 / 知识库跨班为空。缺哪个先记下。
  • 分工建议：一人测试收口、一人容器与流水线、一人观测与压测；每段交叉验收。

二、测试收口与门禁

  • 把上表的检查写成用例落进 apitest/cases/ 或单元测试目录；涉及模型等待的用例（如教师改分优先）用测试替身缩到秒级。
  • 聚合进 make check：接口与单元用例全量执行，退出码 0 为绿；安全反例用例由 make check-security 单独执行、高危 0 条为绿——两条命令并列挂进持续集成（CI）。
  • 本课必做：先红后绿留全程证据——故意改坏一处（改错一个期望值或比较条件即可），跑出红的一屏；修复后复绿，连同修复提交一起归档为 reports/gate-red-green.md（改坏的位置、红屏与退出码、修复提交编号、绿屏与退出码 0 四件齐全，命令可当场复跑）。
  • 主干分支（main）开启保护：准入流程为 AI 初稿 → AI 自审（Harness 读规则文件逐类过）→ 脚本门禁（make check / make check-security）→ 人工确认（只确认机器判不了的需求意图，并补一条用例或规则）→ 交叉评审（peer review）→ 合入主干分支（main）；未过门禁的提交进不去。

三、容器化：一键启动

  • 写多阶段 Dockerfile：构建与运行分离，最终镜像不含源码与构建工具；密钥与环境相关的值一律不进镜像，运行时从环境变量注入。
  • 写 Compose 文件：应用、MySQL、Qdrant 三服务，声明依赖与健康检查——应用等数据库就绪再启动，不靠脚本里的等待循环。
  • 验收：换一个目录（最好换一台机器）按 README.md 一条命令启动，全部服务就绪，无需口头补充任何步骤。
  • 镜像编号取自构建时的提交编号——先记下这条规矩，流水线一节要用它反查。

四、流水线：推送即构建

  • 自动构建配置入库（如 GitHub Actions）：检出 → make check → make check-security → 构建镜像。跑的命令与本地完全同一条——本地与线上两套标准等于没有门禁。
  • 推送一次提交，记录自动构建的编号与对应提交——验证镜像编号能反查提交，这是「线上跑的是哪个提交」的证据链。
  • 数据库变更一律走三步走（扩 → 迁 → 缩）：本课如有索引改进涉及改表，只走到「扩」与「迁」，删旧列等确无回退需求之后；当前处于哪一步写进变更说明。
  • 发布前检查就绪探针：新实例数据库连不上就不接流量。

五、观测：面板与告警

  • 指标按技能命名（如 skill_invocations_total 带 skill 与 status 两个维度），复用上一课日志七列的字段口径；失败率在面板上算，不单独上报。
  • 面板至少三张图：三个技能调用量分线曲线 / 每技能错误率 / 接口 P95 与任务队列深度并排（上一课异步判据的运行形态）。
  • 告警至少一条写成判定：观察量 + 持续条件 + 动作（如某技能错误率 5 分钟连续高于 1% → 通知负责人 → 附面板链接）。
  • 告警必须真触发过一次：人为制造几分钟连续失败（上一课的越权重放即可），通知在设定时间内送达，触发记录归档。

六、压测、改进与真实用户

  • 轻量端（H5）：复用同一套接口与认证，服务端配好跨域声明；手机浏览器能走通最终验收的四步——登录取令牌 → 提交作业返回 202 与任务标识 → 轮询看 pending → running → succeeded → 换另一班账号查别班讲义拿 404，且这次经历落进审计日志七列。
  • 至少 3 名使用者实际使用，每人一条反馈记录写入 reports/feedback.md：会话标识、触发的接口、观察到的返回、期望与实际的差异。每条反馈要么进任务清单、要么写明为什么不做；使用者踩出的新坑写成用例进套件。
  • 压测脚本入库（如 k6，参数走环境变量）：对提交、查询、检索三个接口分别加压，记下吞吐与 P95 随并发的变化，标出饱和点。口径：提交接口压「接收能力」，批改吞吐由消费者数量决定，分开量。
  • 至少一项改进（加索引或加缓存）并在同一脚本同一参数下复测；压测脚本与两轮结果写入 reports/bench.md：同一脚本、同一参数下的吞吐、P95、错误率三数，附瓶颈归因与改进提交编号——最终报告「复盘」一节用这里的前后数字。

七、提交前核查清单（逐条打勾）

  • 门禁：make check 与 make check-security 两条命令并列全量；故意改坏被拦的先红后绿证据齐（reports/gate-red-green.md：红屏、修复提交、绿屏）。
  • 可复现：干净目录 docker compose up -d 一键启动成功；Dockerfile 与 Compose 入库；镜像无密钥、无源码。
  • 流水线：推送后自动构建通过；镜像编号反查提交走得通；本地红推送必失败。
  • 观测：面板三张图都能看到三个技能；告警真触发过一次并留通知记录。
  • 验证：reports/bench.md 两轮数字同脚本同参数；至少一项改进生效且有归因；3 名使用者反馈写入 reports/feedback.md 且有去向。
  • 清单与规则：AI 生成代码的核查口径写进 Harness 会读取的规则文件（AGENTS.md 与 .cursor/rules/），覆盖七类——接口入口、业务逻辑、数据库、公共函数、错误处理、安全、性能，每类写明靠什么手段查（AI 自审 / 脚本 / 人工确认）。
  • 交付：全部证据归档仓库根目录 reports/——审核记录至少 3 份（reports/review-01.md 等，每份写全「用什么手段查 / 查了什么 / 判据 / 结果」，至少 2 份由 AI 自审或脚本门禁发现）、高风险三查（reports/risk-concurrency.md / risk-transaction.md / risk-authz.md）；交叉评审（peer review）——组内另一人从换目录启动开始，把最终验收的四步演示独立走一遍，返回码不符处记为展示前待修项。

流水线是一条单行道：运行中发现问题就回到提交重走一遍，不在运行中的容器里手改文件——改的是代码，不是实例。密钥照旧只进各人本机的 .env 与部署平台的环境变量。
