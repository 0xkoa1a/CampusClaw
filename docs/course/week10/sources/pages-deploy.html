部署与发布

这一页填第三道沟：部署靠手工搬运。推送即构建——提交一进主干，测试、构建、发布由流程自动走完；数据库变更不一步到位，分三步走完再收尾；新版本接流量之前，先过就绪探针。发布从「一个人的手工动作」变成「一条有记录的流程」。

先说清几个词

这一页用到的词先在这里讲明白。

持续集成CI（continuous integration）：提交触发的一段固定流程：检出代码 → 跑测试 → 构建镜像 → 推进制品库。配置写在仓库的文件里，不在任何人的脑子里。俗称自动构建。
持续部署CD（continuous deployment）：构建通过后，把新镜像发布到运行环境并替换旧版本。与持续集成合称 CI/CD。
expand–migrate–contract：数据库变更的三步走——先扩（新旧并存：加新列新表）、再迁（把旧数据搬过去，双写）、最后缩（确认无回退需求后删旧）。任何一步出问题都能停在中间态而不丢数据。
滚动发布：新旧版本逐个实例替换，全程总有一个版本在服务。与「停机换版本」相对。
就绪探针readiness probe：新实例接流量前的体检——数据库连不上就先不接。上一页 Compose 里管启动顺序，这一页管发布。
存活探针liveness probe：运行中的巡检——进程卡死就重启。它不负责「接不接流量」，只负责「活没活」。
RPO / RTO：两个恢复目标。RPO（recovery point objective，恢复点目标）＝最多丢多少数据（备份间隔决定）；RTO（recovery time objective，恢复时间目标）＝最多停多久（恢复流程的时长决定）。定这两个数，比「要高可用」这句话有用得多。

1推送即构建

流程配置入库；本地那条门禁命令，在自动构建里原样再跑一遍。

# .github/workflows/ci.yml —— 提交即触发
name: ci
on: [push]
jobs:
  check-and-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make check            # 与本地同一条门禁
      - run: make check-security
      - run: make image            # 构建镜像并推入制品库
自动构建里跑的必须是本地那条命令——本地一套、线上另一套，等于门禁有两套标准，形同虚设。判定：本地跑绿的提交，推送后自动构建也绿；本地红的，推送后失败并挡住发布。

2数据库变更：三步走

代码可以回滚，数据不能——所以表结构的修改永远不与代码同一步生效。

规约里若有字段变更，任务清单先落三步走的中间两步（扩与迁），缩放到确无回退需求之后——这也是变更归档时写清「当前处于哪一步」的原因。

3发布的体检与底线

新版本接流量靠就绪探针；万一整个流程失败，靠的是事先定好的两个恢复目标。

检查时机回答什么不过会怎样
就绪探针新实例接流量之前依赖都连上了吗不接流量，发布停在旧版本
存活探针运行中，周期执行进程卡死了吗重启实例，事件进日志
备份与恢复上线前定 RPO / RTO最多丢多少、最多停多久没有这两个数，故障时长没有上限承诺
一句话记住：代码可以回滚，数据不能——数据库变更分三步走，新版本接流量先过就绪探针。
