自动化测试与门禁

这一页填第一道沟：把散在各课的验收判据收成一条命令 make check，任何人任何机器执行它得到同样的红绿，并把它接到合并流程上当门禁。质量不是这一课才开始——从写规约、点失败路径起就在积累，这一课只是收口。

先说清几个词

这一页用到的词先在这里讲明白。

测试金字塔test pyramid：用例按层次分底座——单元测试多而快（一个函数、一个判定），接口测试居中（一个请求的契约），端到端少而慢（整条链路）。底座越厚，红了之后定位越快。
单元测试：只测一个最小单元（一个函数、一段判定逻辑），不碰数据库与网络。快，所以可以很多。
接口测试：对一个 HTTP 接口发请求、断言返回。项目里 apitest/cases/<URL>/<方法> 存的就是这一层。
测试替身test double：替被测单元顶班的假依赖——模型调用、外部服务。不用真等一次几十秒的批改，用替身立即返回固定值。
可追溯矩阵：需求 / 规约条目与用例的对照表。每个规约里的场景至少对应一条用例——没有用例对应的场景，就是没人守的门。
先红后绿：新用例先跑出红（证明它真的在测东西），修完再跑出绿。一上来就绿的用例，无法证明它测的是这条路径。
等价类与边界值：把输入分成「同一类行为的组」，每组挑代表值；再专挑边界（0、空串、刚好越界）。两个词合起来回答「用例要写几条才够」。

1从手工验收到套件

收口动作只有三步：把当堂跑过的判定写成用例、挂进一条命令、接到合并。

收口步骤动作完成判定
① 写成用例把当堂跑过的判定落进 apitest/cases/ 或单元测试目录，三段式照搬用例随仓库提交，别人能执行
② 挂进命令接口与单元用例聚合进 make check；安全反例由 make check-security 单独跑，两条命令并列一条命令全量执行，红则退出码非 0
③ 接到合并主干分支（main）开启保护：脚本挂进持续集成（CI），make check / make check-security 非 0 的提交进不了 main故意改坏一处，合并被挡
收口不是补写「质量意识」——质量从写规约、给每条场景配验收时就开始积累了。这一课只是把已有积累变成可反复执行的证据。

2按技能写检查

每个必做技能至少一条检查；技能的行为约束是现成的，缺的只是把它写成用例。

技能行为约束（一直就有）检查写法（三段式）
解题引导直接要答案时，不给出最终答案学生提问「直接告诉我最终答案」→ 期望回答不含答案行，只含引导步骤
作业批改教师改分后，以教师分数为准教师改分 → 再触发一次自动批改 → 期望分数不回退
错题讲解不整段贴出标准答案要讲解 → 期望回答里不出现与标准答案整段相同的内容
知识库跨班检索不到他班内容换另一班账号查他班讲义 → 断言返回 404（跨班一律 404，单侧过滤 + fetch-then-check）
这四条全是接口层用例：发一次请求、断言返回，不需要替身。需要替身的是涉及模型调用的等待——替身让「批改后以教师为准」这条用例从几十秒缩到秒级，用例才能进每次提交都跑的门禁。

3门禁跑起来长什么样

一条命令、退出码说话——这是后续自动构建要消费的信号。

$ make check
ok   apitest/cases/POST /api/materials/upload        12 passed
ok   apitest/cases/GET  /api/knowledge/search        31 passed
FAIL apitest/cases/POST /api/skills/grade/ask        1 failed
     解题引导：直接要答案时不应给出最终答案
make: *** [check] Error 1        # 退出码非 0，合并被挡住
故意改坏一处、跑出上面这样的红，是本课必做的一步——门禁要先用一次「真的拦住了」来证明自己存在。之后修复、复测变绿（make check 退出码 0），把红屏、修复提交编号、绿屏写入 reports/gate-red-green.md，最终验收时当场复跑。
一句话记住：自动化测试的主要用途是守住旧功能——每个必做技能至少一条检查，红则退出码非 0，挡在合并之前。
