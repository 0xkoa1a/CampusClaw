可复现构建与制品

这一页填第二道沟：环境长在个人机器上。容器把「能跑的完整条件」打进一个镜像里——依赖、运行时、启动方式全部固化；Compose 把应用与数据库、向量库的关系也写进文件。从这一页起，「能跑」的定义升级为：换任何一台机器，一条命令起来。

先说清几个词

这一页用到的词先在这里讲明白。

镜像image：一个只读的打包产物——代码、依赖、运行时（跑程序所需的基础软件环境）、启动命令全在里面。类似一份装好系统的安装盘，谁拿到都是同一份。
容器container：镜像跑起来的实例。同一镜像起的两个容器，内部环境完全一致——这就是「环境一致性」的落点。
Dockerfile：镜像的构建说明书，一行一个步骤。说明书入库，构建可复现：同提交同产物。
多阶段构建multi-stage build：构建（要编译器、源码）与运行（只要产物）分成两个阶段，最终镜像只留运行所需——小，而且不含源码与构建工具。
Compose：多容器的关系说明书——应用、数据库、向量库各一个容器，谁连谁、开什么端口、按什么顺序就绪，写在一个文件里。
制品库artifact registry：存镜像的地方。推送带编号的镜像进去，线上拉的、本机测的都是同一个——版本可追溯从这来。
配置外置：镜像里不进任何密钥与环境相关的值，运行时从环境变量注入。这是上一课密钥规矩的延伸：镜像会被人拿到，里面的值等于公开。

1构建说明书

一份多阶段 Dockerfile，构建与运行分离；密钥与配置一律不进镜像。

FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./backend/cmd/server

FROM debian:bookworm-slim
COPY --from=build /out/app /usr/local/bin/app
COPY --from=build /src/web/dist /var/www/html
EXPOSE 8080
ENTRYPOINT ["/usr/local/bin/app"]
两个阶段像两道车间：第一间把源码加工成二进制，第二间只把成品和静态页面装车。最终镜像里没有源码、没有编译器——被拷走也不泄漏构建细节。配置与密钥靠运行时环境变量注入，.env.example 留空的规矩原样适用。

2一键启动与就绪

Compose 文件写清三个服务的关系；应用起来不等于能用——就绪探针说了算。

服务在 Compose 里的角色就绪判定
应用（本镜像）对外提供接口，连接另外两个服务就绪探针通过：数据库连接可用、依赖检查通过
MySQL业务数据；先于应用就绪容器内置的健康检查命令通过
Qdrant向量检索；先于应用就绪服务端口可访问
「应用先等数据库就绪再启动」由 Compose 的依赖与健康检查声明表达，不靠启动脚本里的等待循环。判定口径不变：换目录、换机器，执行同一条启动命令，服务全部就绪即为可复现——这正好是「按 README 从零启动」的容器化形态。

3不可变制品

镜像打上编号进制品库，之后只增不改——要改就改代码重新构建。

编号即身份

镜像编号取自它构建时的提交编号。由此「线上跑的是哪个提交」从口头答案变成可查记录：线上镜像编号 → 反查提交 → 反查这次提交跑过哪些用例。三个问题一条链答完，第三道沟（部署靠手工搬运）的病根也在这里被拔掉。

怎么看到：查线上容器的镜像编号，回到仓库找对应提交，再找这次提交的门禁记录——三步都能走通即为可追溯。

不许在运行中的容器里手改

线上出了问题直接进容器改一个文件，等于镜像是 A 跑的是 A'——下一次重启回到 A，改动无声消失，而且没有任何记录说明 A' 存在过。修复永远回到提交走流水线。这条规矩有个名字：不可变制品——改的是代码，不是运行中的实例。

怎么看到：重启容器后再查那个文件——手改过的会复原；用提交走流水线的会随新镜像生效并留下记录。对比一次就记住了。

一句话记住：同一提交构建出等价镜像，镜像编号反查提交——环境一致性与版本可追溯，都是这条链的副产品。
