测试、交付与运行验证

到现在为止，「能跑」的证据都在各自的机器上：手工点过一遍、当堂跑过命令、自查文件里记着红绿。这一课把这些证据收成一条从提交到上线的流水线：一键测试挡住坏提交，容器让环境可复现，观测让系统上线后看得见，最后交给真实用户并用压测回答「它扛得住吗」。前几课攒下的每一条判据，这一课全部变成常驻检查。

先说清几个词

这一课用到的词先在这里讲明白，后面各页不再解释。

回归regression：改了 A，没动 B，结果 B 坏了。回归测试就是每次改动后把旧功能重新跑一遍——自动化测试的主要用途不是「找新 bug」，而是「守住旧功能」。
质量门禁quality gate：合并前自动执行的一组检查，不通过就挡住合入。make check 与 make check-security 这类脚本只是执行手段；把它们挂进持续集成（CI）与主干分支（main）保护、退出码非 0 就进不去，才叫门禁。
可复现构建reproducible build：同样的提交，在任何机器上构建出等价的产物。依赖版本锁定、构建步骤写成文件，是它的两个前提。
不可变制品immutable artifact：构建产物（容器镜像）生成后不再改。要改就改代码重新构建——不在运行中的容器里手改文件。
就绪探针readiness probe：回答「现在能不能接流量」。数据库还没连上就先别把请求分过来。
存活探针liveness probe：回答「进程还活着吗」。卡死了就重启它。
可观测性observability：只靠外部手段推断系统内部状态的能力。三根支柱：指标、日志、追踪。
P95：把一批响应时间从短到长排列，第 95% 位置的值。上一课用它验收请求响应时间，这一课用它做性能基线。

1本课回答两个问题

一个是「凭什么敢交付」，一个是「上线之后凭什么放心」。

凭什么敢交付

不是「我测过了」，而是「任何人执行同一条命令，得到同样的绿」。前者的证据在一次人的操作里，后者的证据在仓库里：测试用例、构建文件、部署配置全部入库，换一台机器、换一个人，产物和结论一致。这条链路是：一键测试 → 镜像构建 → 自动部署。

上线之后凭什么放心

不是「应该没问题」，而是「出问题能在用户发现之前看到」。观测三支柱把系统内部的状态翻译成三张可见的表：指标（聚合的数）、日志（单次的事件）、追踪（一次请求的全程）。再加上压测先量出容量上限，上线才算有底气。

两个问题共用同一条思路：把判断从「人的一次性动作」变成「可重复执行的判定」。前几课给功能、异步、安全写的三段式判据，这一课统一收进这条流水线。
