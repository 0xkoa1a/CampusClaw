# 第 8 课要求：异步任务与消息队列

## 动机与主线

原有批改链路在一次 HTTP 请求内调用模型并等待结果，容易遇到请求超时、并发占用和失败后无法恢复。异步改造让提交请求在任务被接受后结束，由独立消费者稍后处理；消息队列负责在请求线程结束后保存和分发待办任务。

异步是接口交互契约，决定请求方何时结束等待；队列是任务保存和分发设施，提供持久化、竞争消费、确认与重投等语义。仅把工作交给后台线程，不能满足任务恢复要求。

## 输入、输出与职责

- 输入：学生提交的待批改内容，以及用于识别重复提交的幂等标识。
- 提交接口：在数据库事务中保存作业提交和待处理任务，经发件箱投递到队列，快速返回 `202 Accepted` 与 `task_id`。
- 消息代理：持久保留待消费消息，允许多个消费者竞争处理；消费者成功写回结果后 ACK，代理收到后才移除消息。
- 消费者：获取任务、调用批改逻辑、保存结果，并发送 ACK。未确认即崩溃或超时会触发重新投递。
- 状态查询接口：按 `task_id` 返回任务进度和批改结果。它只读任务记录，不触发执行。
- 任务存储：持久化任务状态、执行次数、错误和时间字段；结果存储以唯一约束实现消费端幂等。

## 数据模型与接口契约

课程给出的提交接口示例为：

```http
POST /api/submissions/1024/grade
```

接口返回 `202 Accepted`，响应示例：

```json
{
  "task_id": "task_01J8Z4Q7",
  "status": "pending",
  "status_url": "/api/tasks/task_01J8Z4Q7"
}
```

按任务标识查询的接口示例为 `GET /api/tasks/{task_id}`。任务成功时返回 `200 OK`，包含 `task_id`、`status: "succeeded"` 和 `result`；示例结果含 `score` 与 `submission_id`。以上是课程示例路径和 schema；材料没有列出提交请求体的完整字段。

任务记录至少包含：

| 字段 | 用途 |
| --- | --- |
| `task_id` | 对外任务标识，用于查询 |
| `task_type` | 任务类型 |
| `input` | 输入参数或其持久化引用 |
| `submission_id` | 关联被批改的作业提交 |
| `status` | 状态机当前状态 |
| `attempts` | 已执行次数，用于限制重试 |
| `idempotency_key` | 业务幂等键，数据库唯一约束的依据 |
| `error` | 失败原因 |
| `started_at`、`finished_at` | 执行起止时间 |

课程明确的完整状态为 `pending`（待处理）、`running`（执行中）、`succeeded`（成功）、`failed`（失败）。消息被消费者取走后任务进入 `running`；执行成功进入 `succeeded`；可重试失败且未达上限时退回 `pending`；永久失败或达到次数上限时进入 `failed`。重试达到上限的消息转入死信队列。

## 队列投递、事务与确认

课程选择**至少一次投递**：代理未收到 ACK 就重投，以免丢任务；同一任务可能执行多次，因此结果写入必须幂等。消费者只有在批改成功并写回结果后才确认消息。消费者在确认前崩溃时，代理会重投。

作业提交记录和任务记录必须在同一数据库事务中写入。课程指定事务性发件箱：事务中写入 `submissions` 和初始状态为 `pending` 的 `grade_tasks`；独立投递器扫描待投递记录并发送至队列，失败后下一轮继续。这样队列暂时不可用时，提交和任务仍有持久记录。投递器可能重复发送，所以消费者需要幂等。

任务结果表对幂等键设唯一约束。同一份提交的同一版本生成相同键，示例为 `grade:{submission_id}:v{version}`；版本或内容变化后生成新键。唯一约束必须在结果写入时生效。入口去重或“先查询再插入”不能覆盖消息重投，并发查询还会产生竞态。重复提交或消费后，同一 `submission_id` 只能有一条生效结果，`attempts` 增加而评分不变。

## 队列选型

课程不固定队列产品，验收以三条判据能否复现为准。已有 Redis 的项目可用列表结构与可见性超时，但需要自行实现重投与死信；需要完整队列语义时可选择 RabbitMQ，由代理提供确认、重投、延迟和死信能力。设计规约应记录具体选型及其语义覆盖。

队列还引入独立运维责任：观测队列长度、消费速率、积压告警、磁盘占用和死信数量。持续增长而不回落的队列长度表示消费能力不足。

## 失败分类与退避

- 可重试错误包括模型服务超时、429、网关 5xx 和网络抖动。增加 `attempts`，未达上限时稍后重试。
- 不可重试错误包括空内容、参数校验失败、技能未启用和密钥无效。直接置为 `failed` 并记录原因。
- 达到次数上限后置为 `failed` 并转入死信队列，保留消息与失败原因，供人工处理或恢复后重放。
- 重试间隔采用指数退避并加入随机抖动。课程示例为约 1、2、4、8 秒逐次倍增；抖动用于错开同时失败的任务，避免重试风暴。

课程要求设置次数上限、退避策略和死信处置，但没有指定最大次数、退避上限或抖动分布的固定数值。规约需自行给出可判定参数。

## 三条验收判据

- **请求不等待批改：**连续提交 **20 次**作业，使用 `curl -w '%{time_total}'` 记录各次响应时间，排序取 P95，并与改造前一次批改耗时比较。P95 应显著更短，响应体不含评分结果。
- **消费者停止时任务不丢：**执行 `docker compose stop <消费者服务名>` 后提交作业并查询状态。提交成功且任务保持 `pending`；执行 `docker compose start <消费者服务名>` 后轮询至 `succeeded`，无需重新提交。
- **重复不产生重复结果：**对同一提交连续发送两次，再通过代理管理界面重发该消息，或在 ACK 前执行 `docker compose kill <消费者服务名>` 并重启以触发重投。结果表中该提交只有一条生效记录，`attempts` 增加且评分不变。

三条判据均按“前置条件 / 操作 / 可观测结果”写入规约。首轮可手动复现，之后纳入 `apitest/cases/` 并由 `make check` 自动运行。实践页要求留存命令、输出和结论；并发与事务记录分别进入 `reports/risk-concurrency.md` 与 `reports/risk-transaction.md`。
