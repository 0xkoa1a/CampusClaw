实践步骤与验收

这一课要动手做的是：把现在的同步批改改成异步执行，并且用三条能当场复现的判据证明改成了。下面是五步实施顺序、三条判据怎么复现、证据放在哪里。每一步的产出都要能在仓库里被找到，而不是只存在于「我跑通了」这句话里。

先说清几个词

这一页用到的词先在这里讲明白。

判据：一句可复核的判断标准，写成「前置条件 / 操作 / 可观测结果」三段式。谁照着做都能得出同一个结论。
P95：把一批响应时间从短到长排列，处在第 95% 位置的值。代表绝大多数请求的实际体感，避免被个别极慢的请求带偏。
复现：换一台机器、换一个同学，按仓库里记下的命令重做一遍，能得到同样的结果。
回归：改动之后把之前已经验证过的判据再跑一遍，确认没有把原来的能力弄坏。
证据归档：把命令、输出、结论存进仓库根目录的 reports/，让别人事后可查。
只读接口：只查询、不触发执行的接口，可以放心反复调用。

1五步实施

步骤产出完成判定
引入消息代理编排文件中新增队列服务，配置外置按仓库说明从零启动后，队列服务处于可用状态
建任务记录任务表结构与迁移脚本，含幂等键唯一约束迁移可重复执行；重复插入同一幂等键被约束拒绝
改提交接口写入任务记录并返回 202 与任务标识；同步调用路径关闭提交响应不含分数；代码库中不再存在请求内调用模型的分支
实现消费者独立执行进程：取消息、调模型、写回结果、确认消费者可独立启停；停止后任务停留在待处理
补状态接口与重试任务状态查询接口；次数上限、退避与死信处置状态接口只读；达到上限的任务转入死信并保留失败原因
顺序不可颠倒：先有能启动的队列与任务表，再改接口、再实现消费者。先改接口而没有落地的消费者，会形成「提交成功但永远停在待处理」的状态，而且分不清是改造没做完，还是消费失败了。
一句话记住：三条判据要能被别人照着复现一遍，得出的结论和你一样。只写「已实现」而没有复现过程，后续课次的回归无从对照。

2三条判据的复现方式

判据一：请求不再等待执行

连续提交 20 次作业，用 curl -w '%{time_total}' 逐次记录提交接口的响应时间，排序后取 P95；与改造前一次批改的执行耗时对比。判定：提交响应时间的 P95 显著小于一次批改的执行时间，且响应体中不含评分结果。

判据二：任务不因进程终止而丢失

用 docker compose stop <消费者服务名> 停止消费者后提交一次作业，查询任务状态；随后 docker compose start <消费者服务名> 并轮询状态接口直至 succeeded。判定：提交返回成功、状态停留在待处理；消费者启动后该任务被自动执行，无需重新提交。

判据三：重复不产生重复结果

对同一份提交连续发送两次请求；再人为制造一次重复投递——在代理管理界面将同一条消息重新发布一次，或在消费者确认前用 docker compose kill <消费者服务名> 终止进程再重启以触发重投。判定：结果表中该提交只有一条生效记录，attempts 增加而评分不变。

三条判据均写入本次变更的场景清单，采用「前置条件 / 操作 / 可观测结果」三段式表述。首轮可以手工复现一次，随后必须转成用例进 apitest/cases/、随 make check 自动跑——否则每次回归都要人重做一遍。后续课次的自动化回归直接以这三条为用例，不必重新设计。

3证据归档

证据存放位置要求
变更四份文件openspec 变更目录（归档后进入其 archive 子目录）动因、设计、需求规约、任务清单齐备
判据复现记录reports/（仓库根目录）三条判据各一份：命令、输出、结论；并发与事务两条按「用什么手段查 / 查了什么 / 判据 / 结果」写全，分别存 reports/risk-concurrency.md 与 reports/risk-transaction.md
队列与消费者观测同一目录队列长度变化、消费耗时（finished_at − started_at）、重试次数（attempts）与死信数量
版本标记提交历史中的标签与本次迭代说明同名，便于回溯对照（如 git tag async-202，以 git tag -l 输出为证）
证据的作用是让判定可复核：换了机器、换了成员，按仓库中的命令与记录仍能得出相同结论。只留下「已实现」的结论而没有复现过程，后续课次的回归无从对照。

4与后续课次的关系

本课产出后续课次如何使用
三条判据固化为回归套件中的用例，一键运行即可复核
判据复现记录（并发 / 事务）归档为 reports/risk-concurrency.md 与 reports/risk-transaction.md，是最终项目报告「高风险三查」的并发与事务两条
任务状态与执行次数纳入运行观测，作为失败率与延迟的数据源
消费者进程纳入部署单元与容量规划，压测时作为独立考察对象
审计所需的执行记录安全检查中据此追溯「谁在何时触发了哪次批改」
