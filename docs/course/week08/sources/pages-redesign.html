系统改造：架构与任务模型

改造之后学生的操作没变，仍然是「交作业 → 看分数」，变的只是批改在哪儿执行、分数怎么拿到。这一页给出改造后的链路、任务记录要存哪些字段、提交接口与消费者各自负责什么，以及为什么写入和入队必须放在同一个事务里。

先说清几个词

这一页用到的词先在这里讲明白。

消费者进程worker：独立于 Web 服务的干活进程。取任务、调模型、写回结果、发确认，可以随时启停与增减。
任务记录：数据库里的一条行，代表一次待办的批改。它是连接「提交」与「执行」两头的唯一凭据。
事务transaction：一组数据库操作，要么全部成功，要么一个都不生效。不会出现「提交写进去了、任务却没建」这种半截结果。
事务性发件箱transactional outbox：先在同一个事务里写下「有待办要做」，再由独立组件把它投到队列。保证只要有提交，就一定有任务。
幂等键idempotency_key：代表「同一件事」的标识，由业务含义生成（例如提交号 + 版本），落在唯一约束上用来挡住重复。
只读接口：只查询、不触发任何动作的接口。可以放心重复调用，刷新、重试、监控探活都不会带来副作用。

2任务记录字段

字段作用缺失后果
task_id对外暴露的任务标识，用于查询调用方无法定位执行结果
submission_id关联被批改的提交记录结果无法回写到正确对象
status状态机当前状态前端与重试逻辑无依据
attempts已执行次数无法限制重试，失败任务无限循环
idempotency_key幂等键，落唯一约束重复投递产生重复结果
error失败原因，供排查与展示失败不可诊断，只能重放
started_at / finished_at执行起止时刻无法度量执行时间与积压

3职责边界与事务一致性

改造中最容易出错的一处：业务写入与消息投递不在同一个原子操作内，会出现「提交了但任务没入队」或「任务入了队但提交没写进去」的情形。

BEGIN;
  INSERT INTO submissions (assignment_id, student_id, content) VALUES (...);
  INSERT INTO grade_tasks (submission_id, status, idempotency_key)
  VALUES (1024, 'pending', 'grade:1024:v1');
COMMIT;   -- 业务写入与任务记录在同一事务
-- 入队由独立投递器扫描 status='pending' 的记录完成，失败则下一轮继续

这种做法称为事务性发件箱（transactional outbox）：先在本地事务中写下待办，再由独立组件把它投递到队列。它保证「只要有提交，就一定有任务」，代价是入队存在短暂延迟，且投递器本身要保证至少一次投递（宁可多投一次，也不能漏投）——消息重复由此产生，由下一页的幂等设计吸收。

另一种写法是在事务提交后直接调用代理投递。它更简洁，但事务提交成功而投递失败时任务即丢失，需要额外补偿；本课要求前一种写法。
一句话记住：改造的本质是把「执行」从请求里搬出去，用一条持久化的任务记录把两头接起来。事务保证这根线不会断在中间。

4结果查询方式

方式做法适用与代价
轮询（polling）前端按固定间隔请求任务状态接口，到达终态即停止实现简单、无状态；代价是无谓请求与最长一个间隔的感知延迟。本课采用
服务端推送通过 SSE 或 WebSocket 在状态变化时主动下发实时性好；需要维护连接与重连，且消费者与连接层要打通。流式会话已具备该通道，可作为拓展
无论采用哪种方式，状态接口都只读取任务记录，不触发执行。接口具备幂等性与只读语义，是前端可以放心重复调用的前提。

5问题与解法对照

原问题改造后的对应机制
超时与响应截断请求只写入任务并投递，响应时间与执行时间解耦
处理单元被长任务占用执行移出请求链路，Web 实例只处理短请求
不可中断、不可恢复查询任务标识 + 状态接口，随时可查
失败无法恢复任务持久化 + 确认与重投
算力无法独立伸缩消费者实例独立扩容，与 Web 实例解耦
峰值无缓冲队列堆积，按消费能力匀速处理
六项中有四项由「执行移出请求」解决，两项（可靠性与弹性）由队列机制解决。这也再次说明：异步与队列解决的是不同层面的问题。
