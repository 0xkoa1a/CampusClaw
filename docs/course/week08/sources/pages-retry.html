失败重试与幂等

既然选择了「宁可多投一次也不丢任务」，同一条消息就可能被消费两次。这一页讲三件事：哪些失败值得重试、重试要有哪三个参数、以及怎么用幂等键和数据库唯一约束把重复吸收掉。

先说清几个词

这一页用到的词先在这里讲明白。

幂等idempotent：同一件事做两次，和做一次的结果完全一样，不会多出一份记录、不会多扣一次额度。
唯一约束：数据库层面的一条规则，同一列不允许出现重复值，第二次插入会被直接拒绝。由数据库判定，比应用代码自己判断更可靠。
可重试失败transient：对方暂时不可用，等一会儿再来有可能成功，例如超时、限流、网络抖动。
不可重试失败permanent：输入或权限本身不成立，重试一百次也是同样结果，例如内容为空、密钥无效。
指数退避exponential backoff：重试间隔随次数成倍增长——等 1 秒、2 秒、4 秒、8 秒……给依赖方留出恢复时间。
抖动jitter：在退避间隔上再加一点随机量，避免一批失败任务在同一时刻集体重试，把刚恢复的服务再次压垮。

1两类失败

类别成因处理本项目中的例子
可重试（transient）依赖方暂时不可用，重试有成功可能按策略重试，次数递增模型服务超时、限流返回 429、网关 5xx、网络抖动
不可重试（permanent）输入或权限本身不成立，重试必然同样失败直接置为已失败，记录原因提交内容为空、参数校验不通过、技能未启用、密钥无效
区分的意义在于成本与信号：对不可重试的错误反复重试，既消耗队列与调用额度，又把真正的缺陷淹没在大量重复日志里。

2重试策略的三个参数

次数上限

每次执行记入 attempts，达到上限即置为已失败并转入死信队列。没有上限的重试会把无法完成的任务永久留在队列里，掩盖故障。

退避间隔

采用指数退避（exponential backoff）：间隔随次数成倍增长，并叠加随机抖动（jitter）。立即重试会在依赖方恢复之前持续施压，也可能让一批任务在同一时刻集体重试，形成重试风暴。

终态处置

达到上限的任务进入死信队列，保留消息内容与失败原因，等待人工介入或依赖恢复后重放。死信队列的长度应纳入观测，其增长表明存在系统性失败，而非偶发抖动。

3重复的两种来源

重复投递

消费者取走消息后、发送确认之前进程终止，代理未收到确认，将消息重新投递给另一个消费者。这是至少一次语义的直接后果，与代码正确性无关。

重复提交

用户在前端重复点击、网络重试或重放请求，使同一份提交产生多条任务。这一来源在同步实现中同样存在，只是异步化之后更容易被观察到。

两种来源的共同要求是同一个：同一份提交的批改只能产生一份结果。因此去重不能只做在入口，必须做在写入结果的那一刻。

4幂等键与唯一约束

做法只有一句话：把幂等键写进结果表，并让它落在数据库唯一约束上。重复的那一次写入会被约束直接吸收，不产生第二条记录。

-- 幂等键由业务含义构成，同一份提交的同一版本得到同一个键
-- MySQL 写法：重复键的插入被静默忽略，语句照常返回成功
INSERT IGNORE INTO grade_results (submission_id, score, idempotency_key)
VALUES (1024, 82, 'grade:1024:v1');
-- PostgreSQL 等价写法：
-- INSERT INTO grade_results (...) VALUES (...)
-- ON CONFLICT (idempotency_key) DO NOTHING;

三个要点：其一，幂等键由业务含义派生，而不是随机生成——随机键每次都不一样，等于没法识别重复；其二，去重依赖数据库唯一约束，而不是「先查询是否已存在再决定是否写入」，后者在并发下存在竞态（race condition：两个请求同时查，都发现「不存在」，于是都写了进去）；其三，键中包含版本或内容标识，使内容更新后的重新批改可以正常写入，而不是被旧键挡住。

判据：连续两次消费同一条消息、或连续两次提交同一份作业，结果表中同一 submission_id 只应存在一条生效记录，且 attempts 递增而结果不变。
一句话记住：去重要落在写入结果的那一条语句上，靠数据库唯一约束判定，而不是靠「先查一遍」。

5常见偏差

偏差表现修正
用查询代替约束先查是否存在，不存在才写入；并发下仍产生重复改用唯一约束，由数据库判定冲突
幂等键随机生成每次执行键都不同，去重失效键由业务标识与版本派生
只做入口去重重复投递绕过入口校验，仍产生重复结果去重落在写入结果的语句上
无上限重试失败任务长期占用队列，队列长度只增不减设次数上限，超限转死信队列
不区分失败类型参数错误被无限重试，日志被淹没先分类，再决定是否重试
