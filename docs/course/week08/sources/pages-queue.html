消息队列：语义与机制

异步只解决了「请求不必等」，但任务离开请求之后由谁保存、怎么分给多个人干、干到一半崩了怎么办，还没有答案。这一页讲消息队列：它是什么、提供哪四项保证、为什么不能用线程或数据库任务表凑合，以及它带来的代价。

先说清几个词

这一页用到的词先在这里讲明白。

消息队列message queue：一个能持久保存待办事项的中间件。可以把它想成一个不会丢的待办清单：有人往里放，有人从中取，办完才划掉。
消息message：清单里的一条记录，描述一件待办工作，通常带任务类型和输入参数的引用。
代理broker：保管这份清单的服务程序，负责存、分发、记录每条消息的状态。
确认ACK：消费者干完之后发的一个回执。代理收到才把这条划掉；没收到就认为没干成，重新分给别人。
解耦：放任务的人不需要知道谁在干、有几个人在干。双方只约定「清单里一条长什么样」，因此可以各自独立启停和增减。
削峰：瞬时涌入的请求先在清单里堆着，干活的人按自己的速度取。峰值被摊平到更长的时间里，代价是等待变久。

1定义与三个角色

消息队列（message queue）

由消息代理（broker）提供的、按先进先出顺序保存并投递消息的中间件——即独立于你的业务进程、专门提供通用能力的基础软件，像数据库一样独立部署、独立运维。消息是描述一次待执行工作的数据单元，通常携带任务类型与输入参数引用。

一句话理解：一个不会丢的待办清单，交给专门的中间件保管，而不是放在你自己的进程内存里。

角色职责本项目中的对应方
生产者（producer）构造消息并投递到队列，不关心由谁执行作业提交接口
代理（broker）持久化消息、按序分发、维护投递状态RabbitMQ / Redis 队列
消费者（consumer）取走消息、执行任务、返回确认批改执行进程（worker）
三者的关键性质是解耦：生产者不持有消费者的地址与数量，消费者可以独立启停与扩容，双方只依赖消息格式这一份约定。

2四项机制

每一项机制都对应一个在朴素方案中无法解决的问题。

持久化（persistence）

消息写入代理的持久存储后才向生产者返回。代理重启、消费者全部退出，消息仍然存在。这解决了「任务只存在于内存，进程终止即丢失」。

竞争消费（competing consumers）

多个消费者订阅同一队列，一条消息只投递给其中一个。吞吐通过增加消费者实例线性提升，且不需要在应用代码里实现互斥。这解决了「多个执行进程争抢同一条任务，需要自行加锁」。

确认与重投（acknowledgement / redelivery）

消费者执行成功后发送确认（ACK），代理将该消息移除；消费者崩溃或超时未确认，代理将消息重新投递给其他消费者。这解决了「执行到一半失败，任务既没完成也没人接管」。

削峰（load leveling）

生产速率瞬时高于消费速率时，请求先在队列中堆积，消费者按自身能力匀速取走。峰值被摊平到更长的时间窗口上，代价是队列等待时间增加。

4投递语义与代价

语义含义代价或要求
至多一次（at-most-once）发出去就算完成，失败不重投任务可能丢失，作业批改不可接受
至少一次（at-least-once）没收到确认就重投，保证不丢同一件事可能被干两次，所以消费逻辑必须幂等
恰好一次（exactly-once）端到端只生效一次需要幂等键与去重配合，跨系统实现复杂，通常不在本课范围
本项目取至少一次：宁可多投一次，也不能丢任务；多出来的那一次由消费端的幂等设计吸收掉。这条选择直接决定了下一页的内容——幂等不是可选的加固项，而是这个选择的必然后果。
一句话记住：队列不负责把活干快，只负责把活保管好、分下去、失败了还能再分一次。

5配套部件与选型

延迟队列与死信队列

延迟队列（delayed queue）支持消息在指定时间之后才可被消费，用于指数退避重试：即让失败的任务「过一会儿再来」，而不是立刻重试；死信队列（dead-letter queue）接收重试次数达到上限的消息，把它们从主队列挪出来单独存放，避免个别失败任务长期占用队列，同时保留可追查的记录。

选型口径

已引入 Redis 的项目可直接使用其列表结构配合可见性超时（visibility timeout：取走后一段时间内别人看不见，超时未确认则重新可见），代价是需要自行实现重投与死信；需要完整语义时选择 RabbitMQ，确认、重投、延迟与死信由中间件提供。本课不要求特定实现，判定标准是三条验收判据能否复现。

引入队列同时引入运维对象：队列长度、消费速率、积压告警与磁盘占用都要纳入观测。队列长度为持续增长而非常态回落，即说明消费能力不足，而非队列本身故障。
