异步：契约与状态

异步把一次交互拆成两步：先「发起」，后「取结果」。学生点提交之后不必等模型算完，服务端先记下这件事、返回一张号码牌；真正的批改在请求之外继续进行，结果凭号码牌来取。这一页讲清这套接口约定、任务有哪些状态，以及异步到底改变了什么、没有改变什么。

先说清几个词

这一页用到的词先在这里讲明白。

异步执行asynchronous：发起之后不原地等结果。服务端记下任务就返回，执行在请求之外继续。
任务task：一次待办工作在系统里的记录。它至少要有编号、类型、输入、状态、执行次数这五项，并且写在数据库里。
202 Accepted：一个状态码，语义是「收到了，还没办完」。用它而不是 200，调用方一眼就能分清「这是结果」还是「这是号码牌」。
状态机：一个任务从生到死能处于哪几种状态，以及什么条件下从一种变成另一种。画出来就是状态机图。
最终一致性：结果不是立刻就有，但只要你持续查询，最终一定会到达确定的状态。中间那段「已提交、尚未生效」的窗口必须被正确处理。
轮询polling：按固定间隔反复查询状态，查到终态就停。实现简单，代价是有一点延迟和一些无谓请求。

1定义

异步执行

调用方发起请求后不阻塞等待结果，服务端接收请求、记录任务并立即返回；执行过程在请求上下文之外进行，结果由调用方凭任务标识在之后查询，或由服务端在完成后通知。相对的概念是同步执行（synchronous execution）：调用方在收到响应前保持阻塞，响应中包含执行结果。

任务（task）

一次可执行的工作单元，在系统中以持久化记录的形式存在，至少包含：标识、类型、输入参数、状态、执行次数。任务被持久化，是本课后续所有机制（重试、去重、可观测）的前提。

异步与并行不是同一概念：异步描述的是调用方是否等待，并行描述的是是否有多个执行体同时工作。单线程事件循环同样可以实现异步。

2接口契约

契约的核心是一句话：这次请求的响应只承诺「已接收」，不承诺「已完成」。

POST /api/submissions/1024/grade
→ 202 Accepted
{
  "task_id": "task_01J8Z4Q7",
  "status": "pending",
  "status_url": "/api/tasks/task_01J8Z4Q7"
}

GET /api/tasks/task_01J8Z4Q7
→ 200 OK
{ "task_id": "task_01J8Z4Q7", "status": "succeeded",
  "result": { "score": 82, "submission_id": 1024 } }
202 Accepted 的语义是「请求已被接收、尚未处理完毕」。用它而不是 200，是为了让调用方从状态码即可区分「这是结果」与「这是凭证」。

3任务状态机

状态是任务模型的核心字段：它决定前端展示什么、消费者取哪些任务、以及失败后是否重新执行。

4改变与未改变

维度同步执行异步执行
响应语义响应中携带执行结果响应中携带任务标识，状态码 202
请求占用时间等于执行时间等于入队时间，与执行时间无关
失败可见性只在当次调用里能看到；进程一重启就没了写成任务状态保存在库里，随时可查、可重试
结果何时确定响应返回时结果就确定了结果稍后才到达（最终一致性），中间存在「已提交、尚未生效」的窗口
总执行时间—不减少，还因入队与调度略有增加
总工作量—不减少，同一段模型调用仍然要执行一次
异步不提升执行速度，它把「等待」从请求链路上移走，并把执行过程变成可查询、可重试的记录。把它当成性能优化手段，是这一课最常见的误读。
一句话记住：异步不改变做完这件事要多久，只改变谁在等、等多久。学生不再等，等的是后台那个进程。

5适用边界

不应异步化的情形

其一，执行时间在毫秒量级的操作：入队与调度的开销会超过收益，且引入了不必要的延迟。其二，调用方必须立即依据结果决定后续动作的链路：登录、权限判定、支付结果确认——这些环节缺少结果就无法继续，异步只会把同步等待改写成轮询等待。其三，结果需要强一致读取的场景（强一致：写完立刻能读到最新值，与最终一致性相对）：异步引入了「已提交但尚未生效」的中间状态，读取方必须能正确处理该状态。

异步引入的新问题

任务积压（生产速率持续高于消费速率）、执行延迟（队列等待时间）、状态不一致（写入与入队不在同一事务中时尤为突出）、以及重复执行（重试与重复投递）。前三项靠监控与容量规划应对，最后一项靠幂等设计应对（同一件事做两次，结果不变，详见「失败重试与幂等」一页）。
