操作日志

前面几页防的是「不该做的做不了」，这一页管另一半：真发生了不该做的事，事后能不能回答「谁、何时、对什么、做了什么、结果如何」。SEC-07 查出的字段缺口就在这一页补齐，并让每一次技能调用都能按标识回查。

先说清几个词

这一页用到的词先在这里讲明白。

审计日志audit log：记操作（谁做的）的日志。与系统运行日志（程序自己打的调试信息）用途不同：后者排障，前者回答责任问题。
操作人actor：发起这次操作的身份。技能调用要记技能背后是哪个用户——只记「系统」等于没记。
技能标识skill id：这次调用走了哪个技能。有了它，才能回答「这次批改用的是哪个技能」——这也是本课验收判据之一。
结构化日志：一行一条、字段固定的日志格式（单行 JSON）。字段固定才能按字段查询与统计，不用人眼翻文本。
请求标识request ID：贯穿一次请求的编号。用它把网关、应用、模型调用三段日志串成一次完整经历的三个片段。
用量与耗时：模型返回的 tokens（模型计费与限流的用量单位，大致对应这次调用处理的文本片段数）与调用埋点的毫秒数。既是成本口径（每次批改花多少），也是异常口径（耗时突增常是失败前兆）。

1字段清单：每列回答一个问题

SEC-07 的判定是「任选一次技能调用，事后回查」。回查能不能成，取决于表里这几列齐不齐。

字段取值来源用来回答什么
操作人请求携带的登录身份谁
操作时间服务端时钟何时
操作类型动作名（如 grade.write、skill.invoke）做了什么
操作对象数据行的 id（讲义 id、提交 id）对哪一条
结果状态成功或错误码成没成
技能标识技能路由用了哪个技能
用量与耗时模型返回与调用埋点花了多少
自动化：回查不做人工翻日志：写成命令或查询脚本，一条命令出结果；七列字段的完整性用断言检查，少一列即失败。
前五个字段（操作人、操作时间、操作类型、操作对象、结果状态）是通用底线，技能标识与用量耗时是本项目特有的两列——没有技能标识，评价「各组自写的技能用得怎么样」就没有数据来源。这两列在落库时就要带上，事后补不回来。

2一条日志长什么样

一行一条、字段固定，这就是结构化日志的形态；按字段查，就是回查。

{"ts":"2026-11-11T10:23:41+08:00","actor":"stu-a1","action":"skill.invoke",
 "skill":"grade-essay","object":"sub-1042","status":"ok",
 "ms":18412,"tokens":3120,"req":"req-8f21c0"}
这条日志能独立回答全部七问：谁（stu-a1）、何时（10:23:41）、做了什么（调用了技能）、对哪一条（sub-1042）、结果（ok）、用了哪个技能（grade-essay）、花了多少（18.4 秒、3120 tokens）。缺任何一列，对应的问题就回答不了——这就是 SEC-07 缺口清单的判定逻辑。

3失败的尝试也要记

审计记的是「发生了什么操作」，不是「发生了什么成功的操作」。

被拒绝的请求是最有价值的记录

SEC-01 ～ SEC-04 的复测本身会产生一批 401 / 403 / 404——这些被拒绝的尝试正是攻击证据：谁在试未登录访问、谁在试越权。如果日志只记成功，这批尝试一条都不留，等真出事时无从追查起点。判定逻辑里加上一行：拒绝发生时同样落一条，状态列为对应错误码。

怎么看到：重放一次 SEC-03 的学生越权请求，随后按该学生加时间窗查日志——能查到一条 status:"403" 的记录即为绿。

日志内容自己也是数据

写进日志的每个字段都经过转义与截断——用户提交的内容若原样进日志，攻击者可以往日志里注入换行与伪造字段（日志注入），让追查的人读到假记录。字段长度截断、内容只记 id 不记原文，是两条低成本的限制。

怎么看到：提交一个带换行符与引号的字段值，查日志——一行仍然是一条完整 JSON，没有被拆成两行或改坏结构，即为绿。

日志查询接口本身也是接口：教师可按学生、技能、时间窗查询；学生不可见——审计数据记录的是全体用户的行为，对被记录者同样敏感。给这个接口做授权判定，与本课第一页是同一条规矩。

4回查的操作与判定

步骤动作期望
触发做一次技能调用（如提交一次批改）调用完成，拿到请求标识
回查按技能标识加时间窗查日志表（写成一条查询命令或脚本并入 make check，输出原文存 reports/audit-recheck.md）至少一条记录命中，字段与七列对齐
核对对照操作人、对象、结果状态与自己刚才的操作一致
一句话记住：审计日志一条记录要能独立回答七问——谁、何时、做了什么、对哪一条、结果如何、用了哪个技能、花了多少；失败的尝试同样要记。
