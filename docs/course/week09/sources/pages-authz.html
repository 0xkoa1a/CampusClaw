越权：判定与修复

SEC-01 ～ SEC-04 的红集中在同一件事上：系统只确认了「你是谁」，没有逐次确认「这件事是不是你的」。这一页讲水平与垂直两种越权、技能工具的鉴权，以及判定应该放在哪一层——修在页面上叫藏，修在数据访问处才叫拒绝。

先说清几个词

这一页用到的词先在这里讲明白。

水平越权：同级身份拿到别人的数据。学生 A1 打开学生 B1 的讲义——身份同级、数据不同。业界也称 IDOR（不安全的直接对象引用）：靠猜 id 就能引用到别人的数据行。
垂直越权：低权限身份执行高权限功能。学生调用只有教师该用的配置接口。业界也称权限提升。
授权判定：「谁能不能对哪条数据做哪个操作」的判定。与认证（确认你是谁）是两件事：认证过、授权不过，照样拒绝。
fetch-then-check：先按 id 把行取出来，再判断归属，不属于就按「不存在」处理。本项目的口径是跨班一律 404——不区分「不存在」与「不是你的」，避免用返回码差异泄露这条数据存在。
单侧过滤：把归属直接写进查询条件（WHERE class_id = ?），查不到就返回空。判定发生在数据库这一层，绕过应用层路由也绕不过它。
技能工具鉴权：技能路由对工具调用做身份与归属判定，并且底层接口不因为「这请求来自某个技能」就免检——工具与普通请求走同一套判定。

1两种越权与各自成因

方向不同，成因相同：判定没有跟着数据走。

水平越权：换一个 id 就能拿别人的

成因是接口只按 id 取行，没有归属条件：URL 或参数里的 id 换成别人的，查询照样命中。后果是可遍历——写个脚本从 1 数到 N，整库的数据都能被拖走，一次请求一条。SEC-02 的红（学生 A1 取到班级 B 的讲义、用班级 B 身份检索到班级 A 知识库）就是这一类。

怎么看到：登录学生 A1，把讲义接口 URL 里的 id 换成班级 B 某条讲义的 id。返回 200 且带内容即红；修复后应得到 404。

垂直越权：菜单挡不住直接调接口

成因是功能只靠页面隔离——教师功能放在教师菜单里，学生界面上看不到，但接口本身没有角色判定。前端的一切隐藏都不是防护：拿到学生令牌，用命令行直接调用配置接口，菜单根本不在链路上。SEC-03 的红（学生改掉技能与提示词配置）属于这一类。

怎么看到：从浏览器开发者工具复制学生令牌，用 curl 直接调用技能配置接口发一次写请求。写成功即红；修复后应得到 403 且数据无变化。

两种越权的共同点：登录检查（认证）都通过了，缺的是授权判定。所以修复位置不在登录逻辑上——登录没错，错在查询与写入的条件里没有归属与角色。

2判定放在哪一层

同一次请求会穿过好几层，判定的可靠性随层次递增：越靠外的层越容易被绕过。

3四条红的修复对照

编号红的现象修复动作复测方式（写成用例，随 make check 跑）
SEC-01不带令牌拿到受保护接口数据入口中间件统一做登录检查，未通过返回 401不带令牌逐个重放受保护接口清单
SEC-02跨班取到讲义、检索到他班知识库检索并入班级过滤（单侧过滤）；讲义取数用 fetch-then-check，跨班一律 404学生 A1 换 id 访问班级 B 讲义；用班级 B 身份检索班级 A 知识库
SEC-03学生改掉技能与提示词配置写入类接口逐次校验角色，非教师返回 403学生令牌重放配置写接口，查数据无变化
SEC-04绕过技能路由直调批改写入成功底层批改写入接口同样校验身份与归属，技能调用不免检不走技能路由直接调用批改写入接口
自动化：复测不是手工点一次：这四条都要写成用例进 apitest/cases/，随 make check 在每次提交时自动跑；人只看红绿与失败原因。
复测必须沿用上一课的同一条三段式记录（前置条件 / 操作 / 可观测结果），只把「当前实际」换成修复后的值。改了判定后「看起来好了」不算数，重放得到绿才算数。

4修复的写法

把归属并进查询条件，是水平越权修复的核心一行；角色判定同理，写在接口入口而非页面。

// 修复前：只按 id 取讲义，谁登录都能拿到别的班的这一行
row := db.QueryRow(
    "SELECT id, title, class_id FROM materials WHERE id = ?", id)

// 修复后：归属条件并入查询，数据库层面就拒绝了越权行
row := db.QueryRow(
    "SELECT id, title, class_id FROM materials WHERE id = ? AND class_id = ?",
    id, currentUser.ClassID)
并入条件之后，还要删掉「先查全表再在内存里过滤」的旧路径——两条路一条安全一条不安全时，总有一天会有人调用不安全的那条。同理，检索侧的班级过滤要在向量库查询与 SQL 查询两侧同时生效，只改一侧等于留了另一条路。
一句话记住：授权判定要跟着数据走——判定写在查询条件里，绕过任何一层路由都绕不过它。
