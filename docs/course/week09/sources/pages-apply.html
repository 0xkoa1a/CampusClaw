实践步骤与验收

这一页把前面的修复串成一条当天能走完的流程：选红、修、用同一条三段式复测、归档前后证据。走完时 SEC-01 ～ SEC-07 七项都有绿判定（或书面处置），注入三件套有反例用例，SEC-08 的实验记录在案且第四步工具层为绿，上一课的异步链路没有回归。

先说清几个词

这一页用到的词先在这里讲明白。

复测：用与发现问题时完全相同的三段式记录（前置条件 / 操作 / 可观测结果）重放一遍。修复的完成标志是复测变绿，不是「看起来好了」。
回归：修复没有破坏原有功能。判定材料是 make check 与上一课的三条异步判据——授权收紧最容易误伤的就是任务提交与查询。
门禁：一条命令，红了就挡住合并。make check-security 覆盖的条目里有高危或命中，退出码非 0。接通后留一次真实挡住的证据：先红（必红提交，退出码非 0）后绿（修复后再跑退出码 0），两次输出连同提交号归档 reports/gate-red-green.md——先红后绿才能证明门禁真的在挡。
证据：修复前与修复后的两个实际值。只写结论（「已修复」）不写值的记录，别人无法复核。
基线：某一时刻各项检查的数值快照（命中数、高危条数）。之后的每次变化都对着基线说——升高了还是降低了。

1五步流程

步骤产出完成判定
① 选红定序每条红标注缺口类别（授权 / 注入 / 资产 / 日志）每条红都归了类，修复顺序定下
② 修授权（SEC-01 ～ 04）应用层角色判定 + 数据层归属条件四条复测全部为绿
③ 补注入反例（SQL / XSS / CSRF）三条反例用例，落进 apitest/cases/三件套各自为绿且常驻回归
④ 处置资产（SEC-05 / 06）轮换记录、清理后的历史、依赖处置记录扫描 0 命中；高危清零或书面登记
⑤ 补日志与做实验（SEC-07 / 08）七列日志与回查记录、实验四步记录回查七列齐全；第四步工具层为绿

2证据与归档

全部落进仓库根目录的 reports/，编号沿用 SEC。文件名从本课起固定：修复前后对照表 reports/security-fix-log.md、实验记录 reports/sec08-experiment.md、基线报告 reports/security-baseline.md——最终项目报告直接引用这些路径当场打开，打不开即无法复核。

文件内容判定
修复前后对照表每条 SEC 的编号 / 修复前实际 / 修复后实际 / 判定每行两个值都在，缺一即未完成
权限高风险记录SEC-02 跨班一条按四件事写全：用什么手段查 / 查了什么 / 判据 / 结果存 reports/risk-authz.md，复测命令可当场复跑——是最终报告「高风险三查 · 权限」的来源
反例用例三件套SQL、XSS、CSRF 各一条，三段式记录用例本体按 apitest/cases/<接口路径>/<方法> 结构常驻，随 make check 跑；三段式记录归档 reports/
实验记录SEC-08 四步的现象与判定四步各有实际现象，不只写结论
基线报告密钥扫描与依赖审计的当日快照注明日期与数值，作为后续对比的基线
修复涉及代码的每一步单独开一条变更提交，提交信息写清依据哪一条 SEC 编号——这样安全修复本身也留了可追溯的记录，与审计日志同一条思路。

3回归：修复不许带来新红

安全修复改的是判定，判定变严后第一个受影响的就是正常功能——所以回归不是选做。

要重跑的三组

第一组：make check 全量功能用例——授权收紧后，合法用户的正常路径必须仍然走得通。第二组：上一课的三条异步判据——任务提交与结果查询都过登录与归属判定，最容易在收紧时被误伤。第三组：本课新增的反例三件套——它们进了回归，注入防护从此不会悄悄退化。

怎么看到：依次跑三组，全部为绿。任何一组出红，先修回归再继续——带着回归的修复不算修复完成。

「功能红了说明判定写严了」不成立——多数情况是归属条件写错了位置或值（例如把班级写成了用户）。回归红的时候先怀疑修复的写法，不要先怀疑用例。
一句话记住：修复的完成标志是同一条三段式复测变绿，且前后两个值都归档在案。
