三类安全缺口

上一课的自查已经把七项检查跑完，红绿都记在 reports/security-precheck.md 里。这一页把那些红摆到一起看：同样的红，成因可能完全不同，修复的位置也不同。分完类，后面的每一页各管一类。

先说清几个词

这一页用到的词先在这里讲明白。

功能用例：验证「该做的做了」的用例。用合法身份走正常路径，期望成功。项目里 apitest/cases/ 存的多数是这一类。
反例用例：验证「不该做的做不了」的用例。用合法身份专走不该走的路径，期望被拒绝。上次自查的 SEC-01 ～ SEC-07 本质上就是七条反例用例；SEC-08 是另一回事——它没有「期望拒绝」的固定答案，要当堂做实验看现象。
攻击者视角：假设自己拿到一个合法账号但想拿更多——换一个 id、换一个班级参数、绕过页面直接调底层接口。安全检查就是站在这个视角写用例。
失效安全fail-safe：出错时往「拒绝」的方向倒。判定逻辑本身出故障、依赖服务挂掉，都返回拒绝而不是放行。
完全中介complete mediation：每一次访问都过判定，不能「入口查过一次，里面就免检」。绕过路由直调接口仍然要被拦，就是完全中介。
盲区：从来没被任何用例碰过的位置。它既不红也不绿——没人试过。注入类漏洞最常藏在盲区里。

1为什么功能测试全绿不等于安全

功能用例站在正常用户一侧，反例用例一条都没有时，很多问题既不是红也不是绿，只是没人试过。

两类用例验证两件事

功能用例问「学生提交作业后能查到分数吗」，反例用例问「学生 B1 能改学生 A1 的分数吗」。前者的绿对后者毫无证明力：授权判定缺失时，正常路径一切正常，越权路径也一切正常。上一课 SEC-01 ～ SEC-04 跑出红，恰好说明这些位置此前是盲区——功能用例从未从这些角度碰过它们。

怎么看到：翻上一课的自查文件，逐条问一句：这条绿是「试过且防住了」，还是「本来就没试过」？把答案写在条目旁边，本课结束时再问一遍。

绿也可能只是「还没试」

SEC-05（密钥扫描）在上一课之前从未跑过，SEC-06（依赖审计）同样。它们第一轮就出结果，恰恰说明此前连基线都没有。红是明确的缺口，盲区是未知的缺口——后者比前者危险，因为连「有没有问题」都回答不了。

怎么看到：数一数项目里的写入类接口，有多少个从未被反例用例碰过（没试过未登录、没试过学生身份）。没试过的数量就是盲区的下限。

判定的依据不是「跑了多少用例」，而是「反例用例覆盖了多少个能被外部触达的入口」。前者是工作量，后者才是安全边界。

2三类缺口

上一课的红归进前两类，第三类由 SEC-05 ～ SEC-07 直接给出证据。注入类没有红条目，因为它是盲区——本课要补上反例。

缺口一：授权判定缺口（SEC-01 ～ SEC-04 的红）

代码只在入口查了「登录没有」，没有逐次查「这条数据是不是他的」；技能路由那一层有判定，绕开路由直接调底层接口就没有。表现为：不带令牌拿到数据（SEC-01）、跨班取到讲义（SEC-02）、学生改掉配置（SEC-03）、绕过技能路由执行了批改写入（SEC-04）。成因是判定放错了层——放在页面或路由上，能被直接调接口绕过。

怎么看到：挑一个 SEC-02 或 SEC-03 的红条目，读对应接口的代码，找到那句查询或更新——看条件里有没有归属或角色。多数情况下只有 WHERE id = ?，没有 AND class_id = ?。

缺口二：注入防护缺口（盲区）

SQL 语句靠拼接、输出原样进 HTML、写接口不校验一次性令牌——这三处不一定有红条目，因为自查清单没有对应的反例用例。它们要靠本课补：各写一条反例，亲手注入一次，看系统接不接。接了，缺口成立；防住了，从盲区变成绿。

怎么看到：在讲义标题的位置提交 <script>alert(1)</script>，打开列表页再查看页面源码——内容原样出现在 HTML 里，就是输出转义缺失。

缺口三：资产与日志缺口（SEC-05 ～ SEC-07）

密钥可能躺在全量提交历史或前端产物里，谁也没扫过；依赖里有多少已知高危，没有基线；操作日志字段不全，事后回答不了「谁做的」。这三项的共同点：不出功能问题，出事就是大事，而且出事前没有任何症状。

怎么看到：把 SEC-07 的字段缺口那一行翻出来——列出日志当前实际有哪些字段，缺哪几个。缺的字段就是这一课要补的列。

一句话记住：红是明确的缺口，盲区是未知的缺口——注入类漏洞最常藏在没人写过反例用例的位置。

3从红到绿的判定口径

观察量取值来源判定
反例用例结果脚本重放 SEC-01 ～ SEC-07 的七条用例（一条命令跑完）期望为拒绝（401 / 403 / 404 / 空结果）；实际放行即红
注入反例结果本课新增的 SQL、XSS、CSRF 三条反例分别得到空结果、无脚本执行、请求被拒，即为绿
密钥命中数全量提交历史与前端产物的扫描非 0 即红，且命中后先轮换再清历史
日志字段缺口一次技能调用后的回查七列缺一即记缺口，本课补齐
修复顺序先红后盲区：红是已经验证防不住的位置，盲区是还没验证的位置。先修有证据的，再补没证据的——但两者都不能跳过，跳过盲区等于把「不知道」当成「没有」。
