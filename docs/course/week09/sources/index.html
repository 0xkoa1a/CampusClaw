安全检查与审计

上一课按七项清单做了安全自查，规则是只记录现象、不修复——密钥命中是唯一例外。这一课接着那份清单往下走：先讲清每一处红说明设计缺了什么，再把防护补进正确的位置，从红改到绿，并把复测的证据归档。安全不是在页面外面加一层补丁，而是把「不该做的做不了」写进代码里做判定的那几行。

先说清几个词

这一课用到的词先在这里讲明白，后面各页不再解释。

攻击面attack surface：系统所有能被外部触达的入口总和——每个接口、每个页面、每份能被上传的文件。入口越多，要逐一设防的位置越多。
信任边界trust boundary：请求或数据从「不可信」跨进「可信」的那条线。每跨一次线，都要重新验证，不能因为上一关过了就免检。
越权：通过了登录检查，但拿到了不该拿的数据或执行了不该执行的操作。登录成功只回答「你是谁」，不等于什么都能做。
注入injection：用户提交的数据被系统当成代码执行。SQL 语句、页面 HTML、发给模型的提示词，都可能是被注入的位置。
审计日志audit log：记录「谁在何时对什么做了什么、结果如何」的日志。防不住的事情，事后必须查得到。
默认拒绝deny by default：没有明确写「允许」的一律拒绝。与之相对的思路是「默认放行，发现问题再堵」，后者的代价是每次都晚一步。
最小权限least privilege：每个身份只拿到完成自己任务所需的最小权限。教师不需要的接口，对教师也不开放。
纵深防御defense in depth：不指望任何单层独自防住，多层各管一段——路由层、应用层、数据层各有一道判定，垮一层不至于全垮。

1本课回答两个问题

两个问题一对「查」一对「改」，混在一起会导致「跑了扫描工具就算做了安全」这类误解。

怎么知道系统不安全

功能用例验证「该做的做了」：合法身份走正常路径，期望成功。安全检查验证「不该做的做不了」：拿到合法身份，专走不该走的路径，期望被拒绝。后者要求换一个视角——把自己当成一个已登录但想越权的用户。

查出来的缺口怎么补

上一课自查的每一处红，都指向一个做判定的位置：授权判定、注入防护、资产保管、日志留痕。修复不是把入口藏起来，而是把判定放回它该在的那一层——页面隐藏挡不住直接调接口，只有写进数据访问的判定才绕不过去。

两条问题是先后关系：先用反例用例把红问出来，再对着红修。跳过第一步直接「加固」，等于对着猜测施工——加固的位置和真实缺口的位置常常不是同一处。
